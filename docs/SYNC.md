# Stage 5 cache and outbox

Each verified account retains its physical database name. Room version 2 migrates the Stage 3 `cached_rows` table in place and adds `outbox`. Credentials stay outside Room in the existing Keystore-backed store. Logout deletes that account's database, including its queued changes.

`CachedGrocyRepository.read` reads Grocy, validates JSON, and caches the last good payload by API path. Failed/malformed reads return that payload with `stale=true`; absence of cached data is an error. Cancellation never becomes a cache fallback. Authentication failure does not overwrite the last valid payload. Since Stage 6, 401/403 also propagate denial instead of returning that payload.

`CachedGrocyRepository.enqueue` durably inserts a UUID client operation ID, HTTP method/path/body, reconciliation GET path, optional expected server representation, and `pending` state before the caller starts account-bound work. The UUID is a local operation identity, not a Grocy idempotency key. No credentials are persisted in the queue. Only `pending` rows can atomically transition to `in-flight`; that transition commits before HTTP dispatch. Successful empty/valid JSON acknowledgements become `confirmed`. Explicit 400/401/403/404/405/422 rejections become `failed`. Timeout, cancellation, malformed success JSON, redirects, other status codes, and 5xx become `needs-review`. A 500 does not establish whether Grocy committed before failing.

Mutation transport disables connection retries and redirects. Failed and needs-review rows are never automatically replayed. On database reopen, every durable `in-flight` row becomes `needs-review`, even if the process died just before dispatch. Pending rows resume only after their owning account is activated. There is no background worker that opens inactive accounts. Switching cancels the old session scope and closes its lease; late completions cannot write to that database or acquire the new account's credentials.

The debug app exposes Settings → Pending changes. It lists the active account's operation IDs, states, and safe error details, plus Refresh changes and Read server state. Reconciliation performs a GET and stores the fresh observation. A supplied expected representation must match the complete server JSON (object key order is ignored); otherwise the operation stays needs-review. Without an expected representation, inspection remains manual. Confirmation here means the desired server state was observed, not proof that this particular HTTP request caused it. For additive operations whose result cannot be established unambiguously, omit the expected representation. No re-send button exists.

This stage provides infrastructure and a debug inspector; production feature callers, WorkManager scheduling, and bidirectional feature screens remain future work. Queue durability is tested through actual file-backed Room reopen plus cancellation/recovery, not an Android process kill. MockWebServer covers possible apply followed by timeout, 500 before apply, 401, malformed JSON, concurrent drains, account separation, stale cache behavior, and migration.

Gate: `mise run stage:5` (including an 80% line coverage check for the cache/outbox repository and transport implementations). JVM Android database tests use Robolectric; they do not claim emulator, phone, or live Grocy validation.

Stage 7 adds durable shopping intent records and `guarded` transport operations. The generic drainer skips guarded operations on refresh and account activation. Shopping synchronization verifies fresh server state and claim ownership before claiming a specific guarded operation directly into in-flight. Interrupted in-flight work still requires review; an unsent guarded record is rechecked before it can dispatch. HTTP acknowledgement payloads are retained to recover acknowledged creates without repeating them. See [shopping protocol](SHOPPING.md).
