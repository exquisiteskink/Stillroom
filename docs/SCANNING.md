# Stage 9 scanning

CameraX uses its lifecycle controller and view-coordinate ML Kit analyzer. The barcode detector is bundled in the APK; frames are analyzed on the device, without storing or uploading images. The white target accepts codes whose bounding-box center falls inside it. Torch and linear zoom controls use the active camera. Camera permission is requested only when Start camera is pressed; manual entry remains available when permission is denied or a camera is absent.

EAN-8, EAN-13, UPC-A, UPC-E, QR, Code 128, Code 39, ITF, and Data Matrix are enabled. UPC/EAN checksums are validated, including UPC-E expansion for checksum/public lookup only. Raw strings, including leading zeros, remain the values displayed and attached to Grocy. One valid unseen code is looked up automatically; multiple distinct detections require a choice. One matched product opens review automatically; multiple matched products require a product choice. Chosen codes are suppressed for the account's scanning session, including after Scan next; Scan same code again explicitly permits that code again. Switching accounts clears the scanning session and review state.

Lookup checks Grocy's own barcode records first. A stale unmatched cache cannot trigger an external lookup. For unknown codes, the app checks fresh Grocy configuration and API support and uses the enabled Grocy plugin with `add=false`. Only eligible validated grocery UPC/EAN/GTIN values can then fall back to a direct Open Food Facts product GET, when public fallback is enabled in Settings → Grocy add-ons. A Grocy 401/403 prevents fallback. Arbitrary QR and other household codes stay within authenticated Grocy lookup and manual product review; Grocy controls any downstream lookup performed by its configured plugin. Arbitrary QR links are never opened or followed. Recognized Grocycodes offer product/stock-entry review or an explicit Grocy browser destination.

The Open Food Facts client sends only a validated grocery code, fixed field selection, and an identifying User-Agent. It sends no Grocy key, cookie, authorization header, photo, location, inventory, journal, user identity, or household record. It does not POST or follow redirects. Public failures permit manual review; previously fetched public suggestions may be shown as cached. No lookup backend was added. ML Kit's own metrics processing is described in [Google's terms and privacy documentation](https://developers.google.com/ml-kit/terms); input processing here is on-device.

Lookup does not create products or stock. Review requires a name and explicit selection of an existing Grocy stock unit and location. Provider-suggested unit/location IDs are offered only when they exist in the loaded choices, and remain editable in review. Reviewed product creation and its barcode attachment use the account outbox with a deterministic attachment identity. Unknown HTTP outcomes require inspection rather than replay. No unit or due date is created from a lookup suggestion. Purchase-unit and positive conversion suggestions can be explicitly reviewed; the conversion is a durable follow-up after the product ID is confirmed. Suggested external image URLs are retained as hints, not downloaded automatically.

Choose Add stock or Use stock before capture. Known or confirmed-created products open a focused review form, limited to the existing purchase and consume operations. Camera activation, zoom and flash selection remain in the scan session while analysis pauses during review; the flash switches off while review is visible and restores the selected setting on capture. Stop camera explicitly ends capture; leaving the scanner disposes the controller. Quantities use the existing conversion/fraction handling and outbox. Scanner purchase requires an explicit package due date, with no date guessed from lookup; purchase/consume undo uses the existing Grocy journal actions where supported. The scanner never books stock merely because a frame was decoded. Confirm add or Confirm use performs the explicit booking. Review status is bound to the operation ID returned by durable enqueue: Saved in Grocy, Waiting to sync, or an unconfirmed outcome directing to Check changes. Next/repeat are disabled during stock transport. Repeat stays disabled for unconfirmed operations; another matching unresolved product/action prevents duplicate submission. Lookup retry repeats only a read, never a stock write.

`mise run stage:9` uses only the existing synthetic Grocy on port 9283. It runs JVM safety/regression tests, a native repository parity test against that instance, lint, coverage, debug/test APK builds, and an instrumented decode of `app/src/androidTest/assets/scanner/multi.png` on an owned API 35 emulator. The emulator's Wi-Fi and mobile data are disabled for the fixture test; no Grocy key is placed on it. This is an instrumented fixture-image scan, not a physical-phone scan or a live-camera hardware test. Temporary synthetic server records and keys and the owned emulator are removed.

Primary implementation references: [bundled ML Kit barcode scanning](https://developers.google.com/ml-kit/vision/barcode-scanning/android), [CameraX ML Kit analyzer](https://developer.android.com/reference/androidx/camera/mlkit/vision/MlKitAnalyzer), [Grocy's archived official API](evidence/stage1/grocy-4.7.1-openapi.json), and [Open Food Facts product GET](https://openfoodfacts.github.io/documentation/docs/Product-Opener/v2/products/get-product-by-code/).

## 2026-10-07 redesign validation

ScannerRoutingTest covers unambiguous vs ambiguous product selection, operation-ID-specific status (including unrelated historical confirmations), and package duplicate suppression with explicit repeat. StockScreenTest checks a signed consume amount renders without a crash in the new stock-history row. These are host tests; no physical camera trial is implied. Central build/test results are recorded in STATUS.md.

Unconfirmed product creation keeps its operation bound to the review and disables next/repeat, including when the product POST succeeded but barcode attachment is unconfirmed. Check changes opens the existing outbox review; Check product status runs the existing synchronization/read flow without replaying unknown requests. Completion requires the repository to confirm the product, barcode attachment, and any reviewed conversion follow-up. ScannerRoutingTest covers this lock.

The compatibility foundation retains barcode-specific amount, unit, store, note and total-price suggestions for stock review. It also adds an optional, explicitly reviewed BarcodeBuddy route using separate credentials and durable uncertain-outcome receipts. Details and current validation: [ADDON_COMPATIBILITY.md](ADDON_COMPATIBILITY.md), [STATUS.md](STATUS.md).

## Shopping-trip scanning

Scanner → Shopping trip appends known barcodes to a persistent account-specific draft without booking stock. Review scanned items pauses capture and offers quantity, price and date editing or removal; blank dates use Grocy defaults. Confirm purchases validates current product units/tare settings and submits durable guarded operations one at a time. Confirmed lines are skipped on subsequent confirmation; uncertain outcomes require Pending changes review. Trips are standalone pantry intake and do not complete grocery-list rows. Use either trip confirmation or Shop purchase for the same purchase. Camera and manual input are supported; vendor broadcast input is deferred. Details: [PRIORITY_ONE.md](PRIORITY_ONE.md).
