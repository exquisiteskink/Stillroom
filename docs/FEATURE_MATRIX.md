# Stillroom feature matrix — Stage 1

Discovery date: 2026-10-06 America/New_York (live response timestamps are 2026-10-07 UTC). Tested the pinned Grocy **4.7.1** and previous minor **4.6.0** fixtures started with `mise run grocy:up`. Grocy remains the system of record and the official web app remains in place.

**No Android feature in this matrix is implemented.** This is the historical Stage 1 discovery. Stage 3 now provides account connection and a navigable shell; the feature screens and offline policies below remain future plans. An OpenAPI path establishes a server capability, not a finished Android feature.

The sources are authenticated responses from the running servers: [capture manifest](evidence/stage1/manifest.json), [4.7.1 OpenAPI](evidence/stage1/grocy-4.7.1-openapi.json), [4.6.0 OpenAPI](evidence/stage1/grocy-4.6.0-openapi.json), [4.7.1 permission hierarchy](evidence/stage1/grocy-4.7.1-permissions.json), [4.6.0 permission hierarchy](evidence/stage1/grocy-4.6.0-permissions.json), and [4.7.1 responses][R47] / [4.6.0 responses][R46]. Response citations use the JSON `label`, which is searchable in each archive. The live schema URL is `/api/openapi/specification`; hierarchy is `/api/objects/permission_hierarchy`. Both require authentication.

All endpoint paths below are relative to `/api`. “CRUD objects” means `GET/POST /objects/{entity}` and `GET/PUT/DELETE /objects/{entity}/{id}`, subject to the exposed-entity restrictions in the live schema. Never write stock or log rows through generic CRUD. Permission names are the actual hierarchy names; a page's permission does **not** establish an API read restriction. The child probes found broad authenticated reads. See [compatibility and access control](COMPATIBILITY.md).

All listed feature flags returned `true` on both fixtures (`feature-config`). No dedicated flag or permission exists for files, user fields, or custom entities in the returned configuration/hierarchy. Flags describe deployment capabilities, not user authorization.

For every future screen: cache reads in an account-separated Room database, mark stale data, and refresh from Grocy. Initial mutations require an online server acknowledgement; no optimistic “done” state or automatic mutation replay. Ktor, Room, and feature screens remain unimplemented. Stage 3 implements Keystore-backed credentials and separate native SQLite caches for authenticated account metadata.

4.7.1 exposes `GET /objects/uihelper_shopping_list`, which supplies joined product/unit/price fields. 4.6.0 returns 400 for this entity; use base rows and reference-data joins there. Both expose stock and chore histories as read-only generic entities. Existence of a generic endpoint does not authorize mutation of a computed view or journal. [R47] / [R46], `shopping-uihelper`, and each live OpenAPI's `ExposedEntityNoEdit` / `ExposedEntityNoDelete`.

The same `product_amount: 2.5` request to shopping `add-product` produces `amount: 2.5` on 4.7.1 and `amount: 2` on 4.6.0. Direct generic row creation preserves `2.5` on both. A future adapter must preserve the server's response and expose this limitation; an endpoint's presence does not prove identical semantics. [R47] / [R46], `fraction-add`, `fraction-add-read`, `fraction-generic-create`, `fraction-generic-read`.
