# Accessibility review — Stillroom Android

Scope: Kotlin/Compose source review, 7 October 2026. Screens inspected: shell/settings/accounts, Today/shared rows, stock, shopping, recipes/cooking, household forms, catalog, scanner/camera, pending changes. No emulator, TalkBack, keyboard, Switch Access, screenshots, or rendered measurements were run by this reviewer. Findings below are source evidence or explicitly calculated token contrast, not a WCAG conformance certificate. WCAG 2.2 is a web standard used here to map accessibility principles; native Android targets should be 48dp, not an assumed conversion from WCAG's 24 CSSpx minimum.

## Component acceptance rules

- Every touch control is at least 48dp in both axes, including icon controls, chips, toggle rows and separate trailing actions; avoid overlapping expanded touch regions. WCAG 2.5.8 specifies 24 by 24 CSS pixels for web targets, subject to exceptions; it does not specify 24dp for Android.
- Normal text contrast at least 4.5:1; actual large text at least 3:1; meaningful control boundaries/icons and focus indicator at least 3:1 against their adjacent colors. Decorative list separators can be softer, but input outlines essential to finding a field cannot rely on a 1.62:1 pale divider token.
- One accessible name per control containing its visible label (WCAG 2.5.3). Use native button/check/select roles and selected/checked/disabled state. Never replace meaningful Text with a contentDescription that removes quantity/date/context.
- Selection, overdue, permission and pending states have explicit text; no color-only distinction. Current navigation destination exposes selected semantics and visible label.
- Buttons retain clear enabled/busy states; label “Saving…” while busy. Prevent double submission without erasing the action label or moving focus to a spinner.
- Confirmation dialogs identify the affected object and consequence; initial accessibility focus is within dialog, traversal remains inside it, dismissal restores focus to trigger. Never announce every camera frame.
- The scanner manual entry remains an equally valid accessible route. Camera permission denial leaves manual entry usable; error includes “Enter barcode” or “Try camera again”. No auto mutation merely from camera recognition.
- Pending-change rows lead with product/task/action and plain outcome, not request IDs or HTTP paths. A change with uncertain result stays available for review until reconciled; unknown writes are never automatically repeated. This serves error prevention and understandable recovery, with WCAG 3.3.4 as a related principle.

## Required validation before claiming completion

Run light/dark token contrast on actual component/background pairs; inspect enabled, selected, error and focus states. On an emulator/device, navigate every main screen and form with TalkBack: verify checkbox names/state, slider value, status announcements, dialog focus restoration, navigation selection, and no duplicate image labels. Test keyboard/tab and Switch Access order, 2x Android font scale, smallest supported screen with keyboard open, landscape, and reduced motion. Include scanner recognized/ambiguous/unknown/permission-denied/loading/error states and pending-change empty/loading/failure/reconciliation states. Source-only review cannot establish these results.
