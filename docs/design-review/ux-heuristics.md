# Stillroom: UX research and heuristic audit

Scope: read-only inspection of the Android Compose UI, ViewModels, `AGENTS.md`, and `docs/SCANNING.md`. This is an expert inspection, not measured usability: no user interviews, physical-camera trials, contrast measurement, or task timing was performed. Severity expresses predicted task risk, not observed failure rate. All recommendations restage existing abilities; no feature expansion is proposed.

## Audience and existing jobs

- Household adult: put groceries away accurately; consume food without reconstructing a database record; check food due soon; shop from a shared list; plan and cook meals; administer household records.
- Restricted household account: find and complete assigned chores/tasks using its actual Grocy user and verified grants.
- Person connecting the app: connect to an existing Grocy server and key; switch an actual account without mixing records.
- Platform: Android API 26+, Kotlin/Compose/Material 3, phone/tablet; CameraX/ML Kit; Grocy is authoritative. Offline/outbox operations can be pending, confirmed, failed, or uncertain. Unknown outcomes must never silently replay.
- Scanning job: “When I handle packages, help me record what I am doing to each product with few repeated decisions and an unambiguous outcome.” Lookup and explicit booking are different actions; a decoded frame must not book stock.

## Screen inventory

Shell: Today, Pantry, Shop, Meals, Household; utility pages Search, Scanner, Settings, Accounts, Pending changes. Tablet sidebar and phone bottom navigation. Search reuses Pantry UI.

Today: current-meal hero, date/greeting, due-chores cards, today's planned-meal cards. Pantry: filters, search, locations, journal; product detail; purchase/consume/open/spoilage/transfer/inventory forms; journal undo. Shop: lists/grouping/store mode; add/edit; purchase review; conflict review. Meals: recipes/weekly meal plan; recipe detail; servings/photo management; ingredient editor; meal-plan editor; cooking mode/timers; consumption review; import review. Household: chores/tasks/catalog; chore/task editors, deletion, history; catalog entity picker and editors; battery charge/history. Scanner: start-camera/manual entry; detected-code choices; lookup result/product choice; unknown-product review; embedded stock detail; repeat controls. Accounts: connection form/QR scan, permission verifier, account switch/logout. Settings: visible sections, child landing, reminders/quiet hours, theme/dynamic color/reduced motion. Pending changes: account-bound outbox and server-state reconciliation.

## Nielsen coverage

1. Visibility: prioritize truthful pending/confirmed/uncertain states; scoped loading and connected account identity.
2. Real-world match: actions “Add stock” and “Use stock”; friendly quantities/dates/names instead of IDs and API enums.
3. Control: proper nested Back, explicit stop-camera, cancel review without mutation, explicit conflict review.
4. Consistency: single chooser/form/button pattern; context-correct required labels and Back labels.
5. Prevention: barcode deduplication without breaking deliberate repeats; date entered deliberately; no stock booking from decode; unknown outcomes do not replay.
6. Recognition: show product, current stock and unit at review; searchable bounded choices, resolved names.
7. Efficiency: persist scan job and camera session; omit redundant code/product selection when unique; restage form ahead of metadata.
8. Minimalism: remove generic heroes and always-visible maintenance forms; disclose transaction metadata and advanced configuration.
9. Recovery: accessible Pending changes, row-specific uncertainty actions, field-specific repair guidance.
10. Help: concise instructions at the point of permission/date/unit ambiguity, with a route to the existing recovery screen.

## Scanner target flow (restaging only)

1. Open Scan; choose existing “Add stock” or “Use stock”. This selection governs current session, not new inventory behavior.
2. Explicitly enable camera for first use; request permission only then. “Enter code” opens supported manual entry; advanced code format remains available when needed.
3. One eligible detection starts lookup; multiple codes open a chooser. Never book from a decoded frame.
4. One known product opens transaction review; multiple products require a named product choice. Unknown code opens existing product review only with edit permission, else explains existing Grocy resolution.
5. Review product, quantity, stock unit and required package due date for Add stock; location/price remain supported quieter fields. Confirm explicitly.
6. Show truthful result: confirmed with supported undo route, pending with sync status, uncertain with Review change. Preserve safe outbox behavior.
7. Return to scanning within same explicitly enabled session; maintain chosen job. Repeated identical packages are permitted after explicit completed handling; continuous frames do not trigger duplicate submissions.

Grocy Android is an interaction reference for action-first repetitive scanning only. This report does not claim a measured comparison, copy GPL source, or expand scanning to unsupported actions.

## Validation needed before implementation signoff

On a physical phone, test: five distinct packages; three identical packages; unknown product with/without edit permission; multiple visible codes; denied camera permission; interrupted connection and unknown HTTP outcome; Android Back from every review; small-height screen and 200% font scaling; account switch mid-lookup. Record task completion, repeated taps, corrections and observed failures. These tests are recommended evidence, not tests claimed to have run.
