# Stage 7 shopping

Shop reads Grocy's shopping lists and rows, products, quantity units, resolved unit conversions, stores (`shopping_locations`), product groups, last-purchased prices and stock locations through the account's Room cache. Multiple lists can be selected and new lists created. Product and note-only items support quantities, notes, completion, editing, and deletion. In-store mode enlarges item text and gives every item action a minimum 64dp control. Store/category grouping comes from product master data and the last purchase's store; note-only items without metadata have an explicit unknown group.

Grocy's shopping row `amount` is in stock units; `qu_id` is a display unit. Input/display conversions use Grocy's resolved factors. The fractions module only handles presentation and input; decimal stock quantities stay numeric in JSON and Room. Generic row creation preserves fractional amounts on 4.6.0 as well as 4.7.1, avoiding the older server's truncating add-product helper. Estimated totals multiply open item stock quantities by known last purchase prices per stock unit. Queued edits are included in the displayed estimate. Missing prices are counted explicitly rather than assumed zero. Completed items are excluded. Price/currency values are ordinary decimals, never fractions.

Turning an item into stock opens purchase review. It shows the product, actual stock-unit quantity, price per stock unit, due date, location, store, and note. Confirmation persists the intent before dispatch. Purchase calls the Stage 6 stock repository with a stable operation UUID and a journal note marker; no second stock implementation exists. A successful purchase then marks the shopping row done, leaving it visible in Grocy's completed items. If the shopping row changes during purchase, the stock booking is retained and list completion opens conflict review without overwriting the changed row or buying again.

## Queue and conflict protocol

Room version 3 retains Stage 5/6 caches and outbox records and adds `shopping_outbox` intent records plus HTTP acknowledgement payloads on the transport outbox. Shopping intents retain their original full row snapshot, proposed values, observed conflict, operation identity, claim ownership, and phase. Repeated pending edits on the same row consolidate while retaining the original baseline. An account switch cancels its work and resets forms; account activation resumes its own queue.

Before replay, a fresh GET must succeed. An offline cached response cannot satisfy a write guard. Any changed or deleted server row opens conflict review, preserving the local intent and server row. The user can keep the server version, or explicitly review and save a merged edit against the observed row. That new edit is guarded again. There is no force-overwrite or blind purchase retry. Pending adds/deletes/edits use stable identities in the existing transport outbox. Their HTTP records, purchases and list-completion records remain `guarded` until shopping synchronization checks fresh server state. The generic drainer cannot dispatch them, including after a process restart. A guarded record is claimed directly into in-flight only by the shopping drainer; any queued dispatch rechecks its row first. Fresh reads reconcile absolute writes when their complete proposed fields match; ambiguous adds without a reliable acknowledgement remain for review.

Grocy has no documented conditional-write or purchase-idempotency API. Stage 7 uses the official custom-object API's UNIQUE primary key as a distributed claim shared by participating Stillroom clients. The first guarded edit creates a hidden standard user entity `stillroom_shopping_sync_v1`, ID `-1700000007`; it contains no credentials and is not shown in the sidebar. Claim objects have deterministic negative IDs derived from entity, shopping row ID, and creation timestamp. Positive household user entities/objects are untouched. A reserved ID belonging to another entity causes a safe failure, never replacement. The server's unique-key check is atomic; a second client cannot acquire the same row claim. Fresh row checks occur both before and after acquiring it. An edit/delete releases its owned row claim after confirmation. Purchase acquires a separate, permanent receipt claim, then releases its temporary row claim when safely complete. Completed items remain editable/deletable; another purchase of the same row remains blocked by the receipt. Repeated purchase submissions, including a second client's stale review, do not dispatch a second purchase.

Claims and item/stock mutations are also transport-outbox operations. There is no automatic claim expiry. An interrupted claim with unknown ownership or an unknown purchase outcome stays in review. A known claim acknowledgement with no durable item dispatch record can resume safely: the absent record proves no item request was sent. A purchase applied despite a lost HTTP response is reconciled using its unique marker, product, amount and active purchase journal entry; it then completes the row without another purchase POST. A changed/deleted row or undone/ambiguous journal does not cause a repeat booking. Receipt objects must remain while their row can still be reviewed for purchase. If a row ID is reused in the same creation second, safety can conservatively block the new item rather than risking a repeat purchase.

Safe guarded writes require the server permission to create/delete standard user objects (`MASTER_DATA_EDIT`, included in ADMIN), in addition to shopping access. When these operations are denied, no shopping edit or purchase bypasses the claim. Unknown/denied shopping grants do not fetch or display list data. This does not implement Stage 1's child proxy.

**Concurrency boundary:** claims serialize Stillroom clients using this protocol. Direct Grocy web/API clients do not participate in these claims, and Grocy provides no compare-and-swap write. Changes observed before a dispatch always cause review, and post-write differences are reviewed. An uncoordinated web/API write inside the final GET→PUT window cannot be given an atomic no-overwrite guarantee by this client. Achieving that guarantee for all writers would require a server conditional-write facility or routing all writers through one coordinating service. Neither is claimed or implemented in Stage 7.

## Validation

`mise run stage:7` runs the debug build, lint, JVM regressions, fractions, shopping coverage, and actual container tests against Grocy 4.7.1 and 4.6.0. Tests use real Room files and production repositories/transports. Two isolated clients edit the same row and race a reviewed purchase: one edit/purchase confirms, the other opens conflict review, with only one purchase journal entry. An offline stale edit leaves the second client's note/quantity untouched; an unchanged offline edit replays once. Add, edit, delete, multiple-list creation, and stock completion are checked through independent official API reads.

A test proxy forwards a purchase to the actual container, then drops its HTTP acknowledgement. The local database is reopened; a second client is blocked by the retained claim and the first reconciles through the journal without another purchase. Proxy response loss is injected; stock quantities and journal rows are from the actual Grocy server. Synthetic lists, products, units, locations, claims, API keys, users and private fixture files are cleaned up. MockWebServer adds controlled simultaneous-client, interrupted-phase, denial and cache/queue scenarios. These are API/container interoperability tests, not phone, emulator or browser UI automation.
